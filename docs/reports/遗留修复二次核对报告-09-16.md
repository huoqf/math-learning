### 1.3 机理确认（读码 + 实测互证）

1. **`responsive={false}` 的早退是上一轮裁切的直接原因**
   `KatexFormula.tsx` L155–158：
   ```ts
   if (!responsive || !outerRef.current || !inner) { setScale(1); return; }
   ```
   → 测量、语义拆行、兜底缩放全部跳过。上一轮 block 模式又叠加 `responsive={false}`，公式必然以自然宽度硬撑后被杀。现已彻底移除。

2. **`min-w-0` 修复的是一处「容器宽 = 内容宽」的失效**
   `KatexFormula.tsx` L169–176 取 `containerWidth = min(自身盒宽, 父容器宽)`。
   父级 `<span>` 作为 flex item 默认 `min-width: auto`，其 min-content 尺寸等于 KaTeX 内容宽（`whitespace-nowrap`），**span 于是无法收缩 ⇒ span 宽 = 公式自然宽 ⇒ 容器宽 = 内容宽 ⇒ 缩放永不触发**。
   加 `min-w-0` 后 span 可收缩到行内可用宽度；而 `KatexFormula` 的 `ResizeObserver` 本就同时观察父级（L275–279），宽度一变即重测得真实可用宽，正向触发缩放。

3. **没有被误改成"全局缩小"**
   `responsive={true}` 恢复后并非所有公式都会被压：444 个 value 行中**仅 5 行触发缩放，0 行缩到硬底线**。绝大多数公式天然放得下，保持 1.0 原尺寸。

## 五、工程副产物：React 19 错误恢复时序（供后续写测试参考）

核对 `Canvas3DErrorBoundary` 时，为了写出确定性用例，把 React 19 的「抛错 → 重试」序列实测了一遍（子组件前 N 次渲染抛错）：

| 抛错预算 N | 渲染调用次数 | 最终 | ErrorBoundary 是否介入 | 日志 |
|---|---|---|---|---|
| N = 1 | 3 | 子节点正常 | **❌ 不介入** | 0 |
| N = 2 | 3 | 子节点正常 | ✅ 介入并自动重建成功 | 1（Error 对象） |
| N = 3 | 4 | 子节点正常 | ✅ 介入并重建成功 | 1（Error 对象） |
| N ≥ 4 | 4 | **降级 UI** | ✅ 介入，重建后仍崩 | 1（Error 对象） |

两个必须记住的坑：

1. **N = 1 时 React 自己就恢复了**：并发渲染抛错后 React 会**同步重渲染整个 root**（`recoverFromConcurrentError`），重试成功即视为「已恢复」，**根本不会通知 ErrorBoundary**。此时 React 会把原始错误**重抛给宿主**（`There was an error during concurrent rendering but React was able to recover by instead synchronously rendering the entire root`）——这是**第二条"外面包 ErrorBoundary 也拦不住"的错误路径**。
2. 该序列**在合跑环境下与单独运行不一致**：同一条 N=2 用例单独跑绿、并进全量套件变红。因此**不要把与 React 内部重试次数耦合的断言写进正式测试**。建议的稳定做法：只保留「持续崩溃 → 降级 UI + 日志恰 1 次」与「直调 `componentDidCatch` 校验 Error 对象透传」两类断言。
