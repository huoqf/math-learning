## 一、现状体检：先把事实校准

你的诊断在方向上是对的，但有三处量级需要校准——它们会影响方案取舍。

### 1.1 职责过载：成立（实测）

| 指标 | 实测值 |
| :--- | ---: |
| `<KatexFormula>` 调用点 | 约 **130 处**，分布 **70 个文件** |
| 其中显式 `responsive={false}` | **1 处** |
| 其中显式 `mode="block"` | **1 处** |
| `renderMixedLatex()` 调用点 | **25 处**（14 个文件） |
| 其中传 `responsive: false` | **2 处** |

**结论**：这台"运行时测量 + scale"的机器，在几乎每一个调用点都被启动，包括 3D 标签、图例、参数控件、表格字段。"大炮与绣花针共用一套算法"——**这个判断完全成立**。

### 1.2 但不是"几千条公式"、也未见"连环重绘"（实测）

| 指标 | 实测值 | 与提案描述的差异 |
| :--- | ---: | :--- |
| 全站 `.katex` 元素 | **2 989** | — |
| `KatexFormula` 实例 | **2 383** | 不是"几千条公式"，是 2 383 个组件实例 |
| **scale < 1 的实例** | **137（5.7%）** | **94.3% 的实例 scale 恒为 1** |
| 全局最小 scale | 0.6901 | — |
| `LayoutCount` 增量（73 路由合计） | **130**（≈1.8/路由） | "每处微小变动都引发连环重绘"**未观察到** |
| `RecalcStyleCount` 增量（73 路由合计） | **127** | 同上 |

**结论**：`ResizeObserver` 没有形成布局振荡，稳定期几乎零额外布局。**性能这条论据不成立**。真正的收益面是那 5.7% 的真实工作负载——这决定了方案一的投入产出比并不高。

### 1.3 微型容器误判：成立，但根因不在"取整"

上一轮已确认：28 处触底**全部**落在 <32px 微型容器，其中 25 处超宽量**恰好 2.00px**、3 处 1.00px。当前 `? 2 : 0` 落地态下**微型容器缩放已归零**，目标达成。

但本轮把根因挖得更深了——**它不是一个"微型容器专属"问题，而是全尺寸范围内普遍存在的判据缺陷**。见第五节。

## 二、方案二（CSS 原生流式排版）：不可行，驳回

### 2.1 给出的 CSS 不合法

```
CSS.supports('display','inline-wrap') = false    ← 浏览器直接丢弃该声明
CSS.supports('break-inside','avoid')  = true     ← 合法，但对 inline 元素在普通流中不产生换行效果
```

实测佐证：把 `.base` 换成"用户原方案"（T2）与"仅改 white-space"（T1）后，三个最长公式的 `baseW/baseH/katexH/越界量` **逐位完全相同**——`display:inline-wrap` 与 `break-inside:avoid` 对布局**零影响**。

### 2.2 为什么 KaTeX 无法靠 CSS 折行（双重机制，均有实测）

**机制一：KaTeX 的 token 之间没有空白字符。**
CSS 折行需要"软换行机会"（soft wrap opportunity），它只在空白字符处或 CJK 字符之间产生。KaTeX 输出的 HTML 里，相邻算子之间**没有任何空白**——所有间距都由 `margin` 实现。所以 `white-space: normal` 只是"允许"折行，却**没有断点可折**。

**机制二：`width: min-content` 陷阱。**
KaTeX 官方 CSS：

```css
.katex .base{position:relative;white-space:nowrap;width:min-content}
.katex .base,.katex .strut{display:inline-block}
```

只改 `white-space` 而保留 `width:min-content`，`.base` 会被压到"最宽不可断片段"的宽度——**公式被压成一条竖线**：

| 公式 | T0 基线 baseW×baseH | T1 只改 white-space | 后果 |
| :--- | :--- | :--- | :--- |
| /derivative ① | 44.13 × 21.31 | **13.19 × 102.56** | 压成 13px 宽、5 行高的竖条，内容越出底边 31px |
| /paired-data-independence ① | 39.17 × 20.88 | **12.92 × 80.56** | 同上，越出 70px |
| /parabola-archimedes ① | 83.92 × 21.31 | **31.48 × 82.25** | 同上 |

**补齐覆盖（T3：撤 `width`、撤外层 nowrap）后仍然不折行**：`/derivative`、`/parabola-archimedes` 的 T3 与 T0 **完全一致**（没折行），`/paired-data-independence` 的高度虽变但内容错位加剧（越出 42px）——不是"折行"，是"塌陷"。

### 2.3 结构面也不支持

- 数据层 937 条 `formula` 中，**48.2% 含 `\frac`/`\sqrt`/`\begin{...}`/`\sum`/`\int`/`\lim`** 等"折行即竖向错位"的结构；
- 项目**已经在用正确做法**：**88.4%** 的 `formula` 已含显式折行标记（`\\` 或 `aligned`/`cases`）。也就是说，折行这件事早已在数据层手工完成，不需要、也不能交给 CSS。

### 2.4 结论

方案二**在 KaTeX 上物理不成立**。若强行推进，等价于改写 KaTeX 的 HTML 输出（在 token 间注入 `<wbr>`），那是自研渲染器的工作量。**驳回。**

> 其中"不该依赖 `transform:scale`"的直觉有一定道理，但正确替代不是 CSS 折行，而是**数据层显式折行**（项目已在做）**+ 修正判据**（见第五节）。

## 三、方案一（组件分流）：方向对，但结论需改写

### 3.1 成立的判断

- **组件确实职责过载**：1.1 节的数字即为证据。
- **微型符号与长推导块的矛盾确实存在**：微型容器（6~15px）里放需要 ~12px 的内容，`(containerWidth-4)/contentWidth` 的固定 4px 余量占比重到荒谬。

### 3.2 不成立的两个判断

**（1）"不需要测量、不需要 scale"——现有 API 已能表达这层区分。**
`responsive={false}` 就是"纯 CSS 符号模式"，且代码里已经这么用了（徽标、标题、单位三处），并配了长注释解释原因。所以问题**不是组件缺少能力，而是用法不一致**：

```
25 个 renderMixedLatex 调用点 → 只有 2 个传了 responsive:false
那 28 处微型触底，全部来自剩下 23 个默认 responsive=true 的调用点
```

**（2）"CSS 原生行内流绝对不会出现缩成黑点或右端裁切"——不成立。**
在 `overflow-x-clip` 的 6~15px 容器里放需要 12px 的内容，关掉 scale 只是把后果从"缩成黑点"换成"**被裁掉右端**"。两者都是错，因为**容器本身就放不下内容**。这不是渲染方案能解决的——这是上游布局需要解决的问题（见第五节）。

### 3.3 更省的等价实现

方案一的目标（把"符号模式"与"展示块模式"分开）**不需要新增两个组件**，只需把已有开关的默认值/用法收紧。它的真正价值是"把约定变成 API 强制"，而 API 已经在位。

**收益面必须诚实评估**：全站 2 383 个实例里只有 137 个（5.7%）真的缩放。为这 5.7% 重构 130 个调用点，投入产出比不佳——**除非**把它和第五节根因修复合并做（同一批调用点，一次改到位）。

## 四、方案三（静态门禁 + 快照页）：推荐，但契约须重写

### 4.1 子项 A：静态长度契约——原提案的阈值当场不成立

对 `src/data`（150 个文件）做全量字段扫描：

| 字段 | 条目数 | 长度分布 | 超 15 字符 |
| :--- | ---: | :--- | ---: |
| `symbol` | **977** | 0-4:307 / 5-8:175 / 9-15:275 / 16-25:127 / 26-40:74 / 41+:19 | **220 条（22.5%）** |
| `value` | 537 | 0-4:13 / 5-8:20 / 9-15:37 / 16-25:89 / 26-40:134 / 41+:244 | — |
| `formula` / `latex` | 937 | 0-4:34 … 41+:744 | — |

`symbol` 最长 74 字符，而且**超限的多数是合理的教学表达式**，例如：

```
len=74  x_Q = \frac{a(b^2 - a^2)}{a^2 + b^2} = …
len=59  \frac{1}{4}(|\vec{a}+\vec{b}|^2 - |\vec{a}…
len=55  \vec{OM} = \frac{1}{2}\vec{a} + \frac{1}{2}…
```

**结论**：按**字段名**设长度上限不可行——`symbol` 字段同时承载"徽标里的一个字母"和"一条完整等式式"。要落地必须按**使用场景**而非字段名切分。

**可行的替代契约（建议）**：

1. 用于**紧凑容器**（徽标 / chip / 表格字段 / 图标旁标注）的公式：**不得含 `\frac`/`\sqrt`/`\sum`/`\int` 或跨行标记**，且字符数 ≤ 某阈值；
2. **块级展示公式必须含显式折行标记或长度受限**（现有 88.4% 基础，存量改动极小）；
3. **行内 `$...$` 片段在 `truncate` / `break-words` / `overflow-hidden` 祖先下必须显式声明免缩放**。

这三条都能用 AST 静态扫描实现，且**拦在写数据阶段**——这是本方案真正的价值，因为它把问题从"渲染时为什么缩了"前移到"这条数据该不该出现在这个位置"。

### 4.2 子项 B：极端用例快照页——强烈推荐

**收益实测**：73 路由全量扫描耗时 **58 秒**（`_eval-scale.mjs`）/ **62 秒**（`_eval-cost.mjs`），并非提案中说的"十几分钟"。但快照页仍有明确价值：

- **确定性**：单页、固定内容、无需逐路由等面板挂载 — 消除本轮反复遇到的"页面抖动伪影"（曾产生 24~80px 假溢出）；
- **覆盖性**：全站 137 个缩放实例集中在少数模式，抓极值 20~30 条即可覆盖全部边界；
- **速度**：预计 < 3 秒 vs 58 秒，**20 倍提升**，使"每次改动都跑一遍"真正可行。

**结论**：推荐，且可直接复用本轮已产出的探针（`audit-clip-strict.mjs` 的"元素数连续两次一致 + 字体就绪 + 稳定 400ms"三段式确定性等待）。

## 五、方案零：修判据的自指缺陷（本报告的核心发现）

这一节回答你问的"为什么会陷入按下葫芦浮起瓢"——**因为判据本身在系统性地制造问题，而不只是在漏判。**

### 5.1 完整因果链（实测）

取三个典型实例（`/function-domain`）：

```
文本             scale   par  outerCW innerSW innerOW baseOW
y=\sqrt{x}       0.8667   94      43      45      43     25
测试点 x0         0.8947  180      55      57      55     57
x=x_0            0.8636  269      42      44      42     28
```

代入组件判据 `needed = (containerWidth - 4) / contentWidth`：

```
containerWidth = min(自身盒宽, 父容器宽) = min(43, 94) = 43
contentWidth   = lineDiv.scrollWidth      = 45
needed         = (43 - 4) / 45 = 0.8667   ← 与实测 scale 完全吻合
```

**三个致命事实**：

1. **`outer.clientWidth` 恒等于 `inner.offsetWidth`**（43 = 43，逐例成立）。因为 `outer` 是 `inline-flex`，宽度是 **shrink-to-fit**——它收缩到内容宽度。于是"自身盒宽"根本不是"可用宽度"，而是"内容宽度"的另一个名字；
2. **`lineDiv.scrollWidth` 恒比真实布局宽多 2px**（45 vs 43、57 vs 55、44 vs 42）。反推 137 个缩放实例的 `content - own` 差值，**绝大多数恰好是 2.00px**；少数出现 1.00 / 5.00 / 8.00，与"该行内 `.katex` 片段数量"相关（每个片段贡献 2px）；
3. 两者叠加 → `contentWidth(own+2) > containerWidth(own)` **恒成立** → **凡未被父级压缩的公式，一律被缩掉 4px 的比例**（对 43px 内容即 13%）。

### 5.2 这个缺陷的规模

| 判定 | 实例数 | 占比 |
| :--- | ---: | ---: |
| 父容器余量充足（`par - own > 20`，公式明明放得下）却仍被缩放 | **104 / 137** | **76%** |
| 父容器的确限制了元素（真实超宽） | 33 / 137 | 24% |

**结论**：那 137 处缩放里，四分之三是**无收益的净损失**——公式本来放得下，被白白缩小了 5~13%，只为消化一个不存在的问题。

这解释了全部现象：

- 为什么"改一个地方→全量 A/B→按下葫芦浮起瓢"：因为**每处改动都是在和一条恒真的判据搏斗**；
- 为什么 2px 容差有效：它恰好抵消了那条虚高，但它只是**抵消症状**，且换到 block 模式（`outer` 是 `w-full`，判据是**正确**的）时就变成真实的裁切代价（这正是实验 C 观察到的那 5 处 0.52~1.36px）；
- 为什么"微型容器"看起来是重灾区：微型容器里这 4px 安全余量 + 2px 虚高的占比被放大到极端，于是最先暴露。

### 5.3 根治方向（**待专项验证，本报告不作为已证结论**）

核心动作只有一个：**换用无虚高的内容宽度度量，并让"可用宽度"与"内容宽度"不再自比**。

候选实现（按推荐度）：

1. **把 `contentWidth` 的取法从 `lineDiv.scrollWidth` 改为 `inner.offsetWidth`**（不受 `transform` 影响、无 2px 虚高；实测 `inner.offsetWidth === outer.clientWidth`，正好推出"放得下"的正确判定）；
2. 或在保留 `scrollWidth` 的前提下，**给 `contentWidth` 减掉"行内 `.katex` 片段数 × 2"的虚高**；
3. **把容差的区分维度从"容器宽度 < 32px"改为"inline / block 模式"**——因为真正的分界不是尺寸，而是 `outer` 是否为 shrink-to-fit：
   - `inline`（shrink-to-fit）：自身盒宽 = 内容宽，判据自指 → 需要容差或改用父级可用宽；
   - `block`（`w-full`）：自身盒宽就是真实可用宽，判据**正确** → 必须保持 0 容差。
   
   现有实现用"容器宽度 < 32px"作为代理变量，**统计上有效但因果上错位**——这也解释了为什么同一份容差代码在 block 模式上会制造裁切。

**必须警惕**：此前实验（"改用父容器宽度作可用宽度"）导致 `/conic-line` 出现 8~9px 真实裁切，说明"放宽基准"确有风险——因为父容器宽 ≠ 该元素可用宽（同行还有 label / 单位 / 徽标等兄弟占位）。**因此 5.3 必须走专项 A/B，不能顺手改。**
