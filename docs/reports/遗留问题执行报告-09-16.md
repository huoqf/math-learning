## 二、项 1：徽标公式过度缩放

### 改动

`src/components/UI/mathPanel/MathInvariantsSection.tsx` —— 徽标内的 `KatexFormula` 增加 `responsive={false}`（并写明理由注释）。

**为什么这是根因修法而非补丁**：该 `<span>` 是 `shrink-0` 且按内容定宽，其"可用宽度"恒等于公式自然宽度。于是 `needed = (containerWidth - 4) / contentWidth` 里那个**固定 4px 安全余量**，在 4~14px 的徽标上占比高达 30%~100%，会把本已放得下的符号误判为"放不下"，压到硬底线（0.55）。徽标本就不参与收缩，缩放对它**只有损害、没有收益**。

### A/B 实测（同脚本、同判据，只切这一个 class）

|---|---|---|
| 扫描到的徽标数 | 222 | 222 |
| **被缩放** | **0** | **81** |

**两点关键结论**：

1. **布局零变化**：A/B 两次的"最宽徽标"清单逐项完全相同（68/104/164/207px…），因为 CSS `transform: scale` 不参与布局。改动**只恢复字形大小，不动任何盒子尺寸**，因此不存在引入新溢出的可能。

## 四、项 3：3D 边界测试固化

新增 `src/test/canvas3dBoundary.test.tsx`，**只保留与 React 内部调度无关的确定性契约**（4 条）：

1. `componentDidCatch` 直调 → `console.error` 第二参数与传入对象**同一引用**（`toBe`），是 `Error` 实例且 `.stack` 非空 → 首次崩溃自动重建（`key` 0→1、`crashed` 回落 false）。
2. `key` 已递增时再次崩溃 → **不重建、不重复记录**，`crashed` 保持 true（防无限重建循环）。
3. 降级 UI → 只渲染提示文案，不渲染子节点。
4. **能力边界** → 事件回调抛错不被捕获（不记录、不进降级、`key` 保持 0）。

**刻意剔除的断言**：子组件"前 N 次渲染抛错"的行为。实测该序列与 React 19 `recoverFromConcurrentError` 的重试次数耦合（N=1 时 React 自行恢复、边界**完全不介入**、日志 0），且**合跑与单独跑结果不一致** —— 断言它会让整个套件不稳定。原因已写在测试文件头部注释里。

> 注：期间为写这条测试实测出一个 React 19 行为 —— `getDerivedStateFromError()` 返回类型为 `Partial<State>`，直接传给 `setState` 不合法（`tsc` 报 TS2345）；已改为 `setState(s => ({...s, ...getDerivedStateFromError()}))`。

## 六、核心组件的三条修法实测对照（实验均未落地）

既然找到了根因（虚假缩放发生在"容器宽 = 内容宽"的退化场景），我在核心组件 `KatexFormula.tsx` 上做了三轮**可回退实验**，每轮都跑全量 73 路由。三处改动在 `updateScale` 的可用宽度口径与触发阈值上。

| 方案 | 做法 | 裁切路由 | 裁切处数 | 最大溢出 | 触底缩放 | 判定 |
|---|---|---|---|---|---|---|
| 生产（当前） | `min(自身盒宽, 父级宽)`；触发 `content > container` | 0 | 0 | 0 | **28** | 基线 |
| 实验 1 | 改用"最近裁切祖先"的内容盒宽 | **9** | **14** | **35px** | 0 | ❌ 否决 |
| 实验 2 | 仅在"自身盒宽 ≈ 父级"时才启用缩放判定 | **5** | **9** | **82px** | 0 | ❌ 否决 |
| **实验 3** | **保留原口径，仅加 2px 整数舍入容差** | **0** | **0** | **0** | **0** | ✅ **通过** |
| 实验 2 另测 | 11 路由定点复测（`verify-fixes`） | 3 条路由 ❌ | — | — | — | 否决 |
| 实验 3 另测 | 11 路由定点复测 | **11/11 ✅** | — | — | — | 通过 |

### 实验 1 / 2 为什么失败（这是本轮最重要的技术结论）

`min(自身盒宽, 父级宽)` 里的**父级宽是 `max-w-full` 的真实约束来源**，不能放宽。

原因链条：`KatexFormula` 的行内外层是 `inline-flex ... max-w-full overflow-x-clip`。当公式自然宽超过父级时，外层被 `max-w-full` 压到父级宽度并**由自身的 `overflow-x-clip` 裁掉超出部分**。所以：

- 用"祖先的裁切边界"作基准（实验 1）→ 基准比父级宽 → 缩放不足 → 被自身 `max-w-full` 裁掉；
- 用"是否被父级压缩"作充分条件（实验 2）→ 在"被压缩"那一支上等同于把基准换成父级宽 → 同样的失败，且更严重（82px）。

一句话：**这条 min 是"绝不裁切"硬不变量的承重结构，放宽它必然塌。**

### 实验 3 为什么成立

实证发现那 28 处的缺口**恰好都是 2px**，而 `clientWidth` / `scrollWidth` 都是**取整整数**：内容真实宽 13.6px 时表现为 `clientWidth=13`、`scrollWidth=14`，凭空制造 1~2px 的"放不下"假象。

实验 3 保留原口径（不碰不变量），只在触发判定上加 2px 容差：

```
- if (containerWidth > 0 && contentWidth > containerWidth) {
+ if (containerWidth > 0 && contentWidth > containerWidth + 2) {
```

结果：**触底缩放 28 → 0，且裁切/溢出仍全 0**，11 条定点路由全绿。它只**减少**缩放（把落在 1~2px 舍入带里的误判排除掉），不改变任何真实超宽场景的判定，因此风险面极小。

**当前状态：实验 3 的代码已按你的规矩回退**（`KatexFormula.tsx` sha256 校验还原为实验前 `5935fdb7…`，与备份逐字节一致）。**等你确认后再落地。**
