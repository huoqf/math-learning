## 1.2 总体结论

**正面**：这个专题的「数形引擎」底子明显强于同类教辅 App 的常见水平——

- 三屏分工清晰：左屏模式/参数/题设，中屏纯几何，右屏推导链；推导链普遍遵循「符号通式 → 代入解析式 → 化简结果」，未出现「空降浮点答案」。
- 中屏特征图元基本标齐：圆锥曲线必画焦点，抛物线必画准线与焦点、焦点弦必画到准线的垂足投影，双曲线必画两条渐近线，`PA ⊥ PB` 时画直角符号。
- 数学真联动：右屏数值由 `src/math/` 纯函数按当前参数实时计算，不是写死的假推导。
- 退化情形有覆盖：判别式 ≤0、二次项系数归零（双曲线平行渐近线 / 抛物线平行对称轴）、`y₁≈y₂` 割线逼切线等均有 warning。

**但存在三类实质问题**，其中第一类会直接把错误结论教给学生：

1. **P0 · 数学结论性错误**：最严重的是把双曲线的「焦半径倒数和」定值写成椭圆的那个公式。

3. **P1 · 卡片名实不符**：卡片叫「四大」，实际挂 10 个节点（含直线与圆等基础页），且描述里点名的「极化恒等式与阿氏圆」不在这张卡里。

## 1.3 P0 级问题（数学错误，会误导学生）

### P0-1 ★★★ 双曲线「焦半径倒数和定值」公式错误

- 位置：`src/data/builders/conicLine.ts`（右屏定理卡、推导链第 3 步）
- 触发：`conicLine` 页 → 曲线切「双曲线」→ 研究视角切「过焦点弦」

代码只对抛物线单独分支，**椭圆与双曲线共用同一条定理**，配文「焦点割线两端点的焦半径倒数和恒等于定值 `2a/b²`」。

**手工验算（a=3, b=2, c=√13≈3.6056）**：

| 直线的斜率 k | 1/\|F₁A\| | 1/\|F₁B\| | 倒数和 | 倒数差 |
|---|---|---|---|---|
| 0.3 | 1.6132 | 0.11337 | **1.7265** | 1.4998 |
| 0.5 | 1.5557 | 0.05623 | **1.6119** | 1.4995 |

- 倒数和随 k 变化（1.73 vs 1.61），**不是定值**；
- 倒数**差**恒为 1.5 = `2a/b²` = 6/4。

**结论**：双曲线的正确恒等式是 `1/|F₁A| − 1/|F₁B| = 2a/b²`（因两交点分属两支，右支焦半径 `ex−a`、左支 `a−ex`，相减时抵消），而不是相加。现文案把椭圆的「和」直接搬到双曲线上，是硬错误。

**并且页面当场自相矛盾**：`src/math/conicLine.ts` 只为抛物线和椭圆设置理论定值，双曲线为 `null`；右屏「焦半径倒数和（定值验证）」这一行于是打印 `理论定值: 0`，与实测 1.61 并列显示。

**旁证**：同一个项目里 `src/data/builders/lineParamT.ts` 对双曲线写的是「**倒数差**」，是对的。同一份知识在两处写法不一致，进一步说明 `conicLine` 这处是笔误式错误。

### P0-2 ★★★ 圆内动弦「倒数和」极值方向写反

- 位置：`src/data/builders/lineParamT.ts`（定理 `reciprocalNote`、高考要点）
- 触发：`conicParamT` 页 → 高考模型「倒数和」→ 曲线切「圆」

原文：圆内动弦倒数和在割线**过圆心（直径）时取得极小值**，在割线**垂直于直径时取得极大值**。

**手工验算（R=3, P₀=(1,0)）**：参数方程代入圆得 `t² + 2(x₀cosα + y₀sinα)t + (d²−R²) = 0`，故 `|t₁t₂| = R²−d² = 8` 为**常数**，而

```
1/|t₁| + 1/|t₂| = (|t₁|+|t₂|) / |t₁t₂| = 弦长 / (R²−d²)
```

即**倒数和与弦长严格成正比**：

| 割线方向 | 弦长 | 倒数和 |
|---|---|---|
| 过圆心（直径，最长 2R=6） | 6 | 0.75（**极大**） |
| 垂直直径（最短，5.657） | 5.657 | 0.7071（**极小**） |

**结论**：直径位置取**极大值**，垂直位置取**极小值**，与文案完全相反。同页的公式 `√Δ/|C|` 本身是对的，只有这段文字结论写反了 —— 属于「公式对、结论反」，学生照着文字记必然做错。

### P0-3 ★★ `conicLine` 抛物线分支的弦长公式写错，且与自己给的数值不自洽

- 位置：`src/data/builders/conicLine.ts`（推导第 3 步 detail 与 latex）
- 触发：`conicLine` 页 → 曲线切「抛物线」→ 研究视角「位置与弦长」

三个曲线类型共用同一段弦长公式文本 `|AB| = √(1+k²)·√Δ/|A|`。但对抛物线，联立后得到的是**关于 y 的**二次方程（`A_y=1`，`Δ = B_y²−4A_yC_y`），由 y 的二次方程求弦长必须用 `√(1+1/k²)`。

**数值验证（p=2, 直线 y=2x, 即 k=2, m=0）**：

- 真实交点 (0,0)、(1,2)，`|AB| = √5 ≈ 2.236`；
- y 的二次方程 `y²−2y=0`，`Δ=4`，`√Δ=2`，`A=1`；
- 页面公式：`√(1+4) × 2 / 1 = 4.472` —— 与页面同时打印的 `|AB| = 2.236` 差了 2 倍。

**结论**：椭圆/双曲线分支（Δ 是 x 的判别式）该公式正确；**抛物线分支公式错误**（应改为 `√(1+1/k²)`）。显示的等式左右不相等，属可直接被学生抓到的硬伤。

### P0-4 ★★ 抛物线「点差法斜率积」指标：符号、实测值、理论值三者互不匹配

- 位置：`src/data/builders/conicLine.ts`（点差法量块）
- 触发：`conicLine` 页 → 曲线切「抛物线」→ 研究视角「中点弦/点差」

| 项目 | 实际内容 |
|---|---|
| 显示的符号 | `k_AB · y₀` |
| 实际算的实测值 | `k_AB · k_OM = p/x₀` |
| 显示的理论值 | `p/y₀` |

而按符号本身，`k_AB · y₀ = (p/y₀)·y₀ = p`（是个**常数**，与中点无关）。三者没有任何两个能对上，「实测 (理论值)」这一对比对学生完全失去意义。椭圆/双曲线分支（`k_AB·k_OM = ∓b²/a²`）是正确的，只有抛物线分支错。

### P0-5 ★★ 椭圆参数页允许 `b > a`，导致两个焦点被画到原点

- 位置：`src/data/registries/conicParam.ts`（`a` ∈ [2,6]、`b` ∈ [1.2,5]，**无 `a > b` 约束**）
- 位置：`src/features/conicParam/components/ConicParamScene.tsx`：`const c = Math.sqrt(Math.max(0, a*a - b*b));`
- 触发：`conicParam` 页 → 把 a 拖到 2、b 拖到 5

此时 `c = 0`，Scene 把 F₁、F₂ 两点都画在原点 O，右屏也显示 `c = 0`。而 b>a 时椭圆焦点实际在 **y 轴上** `(0, ±√(b²−a²))`，同时「长半轴 a / 短半轴 b」的命名也反了。

**这是与项目自身契约的直接冲突**：`discipline-specs.md` 第 8 节明确要求「椭圆预设 a,b 必须满足 a > b > 0」；`conicProperties`、`conicHomogenization` 都做了 `b ≤ a − 0.01` 的钳制，只有 `conicParam` 漏了。页面仅有一条文字 warning，图形仍然是错的。

### P1-5 参数域钳制造成的「滑块空转」（假联动）

- `conicProperties` 离心率 `e` 滑块范围 [0.1, 2.5]，但 math 层 `safeE = min(0.99, max(0.01, e))`。椭圆模式下 e 从 0.99 拖到 2.5（约占行程 60%）时 **b、离心率数值、图形全部冻结**。
- `conicProperties` 位置角 `t` 范围 ±(π−0.05)，但 math 层把双曲线的 t 钳到 ±1.35，滑块后半程 P 点同样冻结。
- 中屏拖拽普遍**未做范围钳制**：`LineParamTScene.tsx`（t 未钳、P₀ 未钳 ±4/±3）、`useVectorPolarizationApolloniusScene.ts`（point 未钳 ±8/±6），可把点拖出画布后「数值框不截断、滑块已截断」，状态不一致。

### P1-6 阿氏圆视图裁切与特征线缺失

- `vectorPolarizationApollonius` 预设 `halfRatio`（λ=0.5）时圆心 x=−5、R=4，跨度 x∈[−9,−1]，而中屏 `xRange` 为 [−8,12]，最左端的外分点 E(−9,0) **被裁出画布**。
- 该页 `apollonius` 模式的设问专门问 `∠DPE = 90°`，但中屏**没有直角标记**；`polarization` 模式的锐角/钝角分界圆也未绘制。
- `conicParamT` 页三种曲线（椭圆/双曲线/抛物线）**均未画焦点与准线**，而 `reciprocal` 模型预设恰恰把 P₀ 放在焦点上；`definition` 模式只画了 +e 方向的单箭头，没有负方向标识、没有 `|t|` 标注，而「t 的正负即方向」正是该页的核心教学目标。

### 4.6 conicParamT 椭圆半轴单源契约与状态写入层不变量治理（A+B 方案）

#### 4.6.1 问题发现与深度排查

在二轮复查中识别出 `LineParamTScene.tsx:290` 存在裸取 `ry={b * scale.scaleY}` 的隐患，经全链路穿透排查确认属于**真实 UI 交互可达的数形分裂 Bug**：

1. **可达性链路**：
   - 椭圆模式滑块为 `["a", "b"]`；虽然 `key === "b"` 具有随 $a$ 动态收紧的上限（$a - 0.01$），~~但控件的 `value` 钳制**仅影响前端显示值，从不回写 state**~~；
     **⚠️ 更正（2026-09-19 22:52，据当前源码重新取值；原文以删除线保留作撤回痕迹）**：该机制描述**错误**。
     `ParamControl` 的**两条写入口都回写 state** —— 数值输入 `commitValue → snapToStep`（`src/components/UI/ParamControl.tsx:281-298`）与滑块 `handleSliderChange → snapToStep`（`:300-311`），
     `snapToStep` 内含 `clamp(snapped, param.min, param.max)`（`:107-113`）并随即调用 `onParamChange`；`:345-347` 的 `clamp` 只作用于输入框草稿 `localValues`（打到一半时的显示兜底），不写 state。
     **真实机制 = "动态上限下移时缺少存量回收点"**：$b \le a - 0.01$ 是**随 $a$ 移动的靶子** —— 它被算进 `param.max`（`LineParamTAnimation.tsx:224-243`，上限公式已与数学层 `getEllipseBMax`（`src/math/lineParamT.ts:123`）**同源**），
     **而 `param.max` 只在"下一次用户操作 b"时才经 `snapToStep` 生效**；当用户把 $a$ 调小、b 的合法上限随之下移时，**没有任何机制回收 state 里存量的 b** ⇒
     出现「滑块显示被就地夹到 $1.49$、state 仍存 $3.49$、中屏按 $3.49$ 画」的分裂（下文第 2 点所述现象与量化后果**完全成立、不受此更正影响**）。
     ⇒ 故这**不是**"控件钳制不回写"的缺陷，而是**"动态上限下移后缺少存量回收点"**的缺陷；§4.6.2 的 B 步（`commitParams → withEllipseInvariant → normalizeEllipseAxes` 统一写入口，5 条写入路径全部收敛）正是针对该根因的修法，方向正确；A 步（`getEllipseBMax` 作 SSOT）使滑块上限与数学层钳制同源，二者共同构成"静态钳制 + 存量回收"的完整闭环。
   - `handleParamChange` 与各模式/预设切换均未对半轴施加任何约束；
   - 用户操作序列：在 $a = 3.5$ 时把 $b$ 拖到上限 $3.49 \to$ 再把 $a$ 拖到下限 $1.5$。此时 state 中留下脏值 `b = 3.49 > a = 1.5`，后续没有任何机制纠正。
2. **量化后果（数形严重分裂）**：
   - **画面**：$rx = 1.5, ry = 3.49$（$ry > rx$），被画成了**纵向椭圆**；
   - **代数**：`calcLineConicIntersection` 内部将 $b$ 钳制为 $1.49$，交点 $A(-1.057, -1.057), B(1.057, 1.057)$ 代回画面椭圆隐式方程误差高达 $-0.4116$（交点脱线）；
   - **状态打架**：滑块显示 $1.49$、state 存 $3.49$、中屏画 $3.49$，三方分裂，且焦点标记因 `b >= a` 判定失败而完全隐匿；
   - **边界硬伤**：若 $a \le 0$ 输入，SVG 规范中 $rx \le 0$ 会导致 `<ellipse>` **静默不渲染**（画面完全消失）。

#### 4.6.2 A+B 方案落地实施

拒绝仅在 Scene 层做表面 `safeB` 的修补策略（不仅产生第 5 处表达式副本，更无法根治 state 脏数据），采取 **A+B 架构级联动方案**：

- **A 步 · 纯数学层单一事实来源（SSOT）**：
  - `src/math/lineParamT.ts` 导出常量 `ELLIPSE_AXIS_EPS = 0.01`；
  - 导出 `getEllipseBMax(a, floor)`：统一下限逻辑（数学层 floor 取 $\epsilon$ 保证 $b > 0$；控件层 floor 取最小值避免区间倒挂）；
  - 导出 `normalizeEllipseAxes(a, b)`：采取「保 $a$、收缩 $b$」策略。对 $a \le 2\epsilon$（含负数、0、NaN）保底抬至 $2\epsilon$（杜绝 SVG 消失硬伤），$b$ 收敛于 $[\epsilon, a - \epsilon]$。合法输入零变更返回，且具备严格**幂等性**；
  - 消费方全面收敛：`calcLineConicIntersection` 移除内联硬编码改调该函数；`LineParamTScene.tsx` 的画面 $rx/ry$、交点与焦点计算同源消费 `axes`；`LineParamTAnimation.tsx` 的滑块动态上限亦以此为准。
- **B 步 · 状态写入侧不变量守卫（根治根因）**：
  - `LineParamTAnimation.tsx` 实现模块级 `withEllipseInvariant(next, conicType)`；
  - 封装统一写入口 `commitParams(value, effectiveConicType)`，全面收敛全组件 5 条写入路径（`handleParamChange`、`handleModeChange`、`handleConicTypeChange`、`handleGaokaoModelChange`、`handleReset`）；
  - 攻克闭包陷阱：在 `handleConicTypeChange` 路径显式传递 `newType`，确保切换椭圆瞬间状态即被归一化。
