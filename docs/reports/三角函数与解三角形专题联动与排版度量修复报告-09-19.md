## 三、按主题的修复要点

### 3.1 联动与边界：把"同一事实"从四处写死收敛为一种算法

**N7** 的根因是"同一约束写了三套边界"：拖拽侧 `min(180−A−5, …)`、滑块侧恒 `max:160`、刻度侧写死 `buildAngleBMarks(60)`。

修复后 `180 − A − 1`（或等价的 `179 − A`）**同式出现在四处**：

| # | 位置 | 角色 |
|---|---|---|
| 1 | `TriangleExtremaAnimation.tsx:207-213` | 滑块动态 `max` 随 `angleA` 联动 |
| 2 | `TriangleExtremaAnimation.tsx:245` | 拖拽 `hi` 上限 |
| 3 | `math/triangleExtrema.ts:543-556` | 纯函数 `clampAngleBOnAChange` |
| 4 | `data/registries/triangleExtrema.ts:20` | 90° 刻度条件 `90 <= maxB − 1` ⟺ A ≤ 89° |

且 `ParamControl` 的滑块量程与输入框钳制读的是**动态 `param.min/max`**，故"滑块 / 输入框 / 中屏"三通道同源，不存在绕过联动的第二写入点（`handleDragA` 在 `angle-transform` 模式下是空操作）。

`clampAngleBOnAChange` 另加一条收紧：`geoMax < 5 → 直接返回 5`，使返回值**恒 ∈ [5,160]**，与注释声明的可行域一致（此前 `Math.max(1, 180−A−1)` 在 A ≥ 175° 时返回 < 5，属"不可达输入固化到断言里"的隐患）。

### 3.2 越界可见性：从"静默消失"改为"显式提示"

N4 / N5 / N9 / N10 / N11 是同一族缺陷——**图形出了画布却没有任何反馈**，右屏照样输出数值，形成"右屏有数、中屏无物"。

采用的统一范式是 `trigLines/DefScene` 已有的 `tanState = parallel | clipped | zero | visible`：

- **N4/N5**：`|tan x| > scale.yMax` 时不再画一条冲出画布的斜线，改为渲染提示胶囊。
- **N11**：把"五点是否越界"抽为纯函数 `partitionFivePointsByView(fivePoints, xMin, xMax)`，**单次遍历双输出**（`visiblePoints` + `outCount`），Scene 只消费结果——避免"判越界"与"挑可见点"两套遍历各自演化。
- **N10**：不再对 Q 做任何缩放 / 反算（旧版 `k = min(1, …)` 恒等于 1，是死代码），改为**让视口完整包容声明域**：`HOMO_VIEWPORT` = x ±3.6 / y ±3.4，声明域 ±3.0 ⊂ 可见域，于是"拖拽自洽"与"渲染自洽"同时成立。

### 3.3 文案与判据同源：判据修了，话也要跟着改

N1 / N6 / N12 / N13 / N14 / N16 / N17 的共同形态是**逻辑已正确、输出仍是旧话**：

- N1：`caseKind` 早已正确区分 `nonacute_no_solution`，但三条文案仍写 `a < h`。修法是文案按 `caseKind` 分支，而非改判据。
- N6：同一面板 `:69` 有 `isTanDefined` 保护、`:135` 没有 → 出现字面 `NaN`；`tan2Alpha === undefined` 被 `?? 0` 兜成 `0.000`，与同面板 `\text{无定义}` 打架。修法是把保护提到所有输出点。
- N16：`data/types.ts` 的 SSOT 约定是 `status !== "正文" ⇒ importance 必须为 extend`；该定理前提自认"选学拓展"却标 `core`。修法走**条目级** `isExtension` 而非改名。

### 3.4 坐标系与量纲：一处契约、两处误用

- **N2**：`InteractivePoint` 的 `cx/cy` 是**数学坐标**（内部 `mathToDesign`），而 `VectorBasisScene` 已先做过一次变换 ⇒ 二次变换把 10 个手柄送到 `(42070, −19975)`（画布仅 840×650）。**长期未被发现的原因**：`corePagesSmoke` / `rightPanelVerification` 都把 `InteractivePoint` mock 成 `() => null`，任何测试都捕获不到位置错误。
- **N3**：角度参数与屏幕坐标不同轴，全库唯此一处误用 `paramDragRange(..., "x")`。

## 四、本轮（最后一批）—— 排版度量体系

### 4.1 字号钳制常量同源

`src/utils/useCanvasSize.ts` 导出 `FONT_SCALE_MIN = 7` / `FONT_SCALE_MAX = 16`，`font` 计算改引常量；两处测试（`tanCapsuleRender.test.tsx`、`trigAndExtremaFixes.test.ts`）从字面量 `16` 改为引用 `FONT_SCALE_MAX`。

### 4.2 宽度模型：从"经验系数"改为"字体实测表"

**问题**：旧模型对 ASCII 统一取 `0.55em`，而实测 ASCII 宽度跨 **0.271em（`,`）～ 1.005em（`W`）**，跨度 **3.7 倍**——单一系数必然一端欠估（对 `W` 欠估 1.83×，对 `,` 超估 2.03×）。旧模型对现有两句文案是**超估**（+14.4% / +16.7%），所以"当前安全"纯属**文案侥幸**；一旦文案改成多宽体字母（如连续 `W`），胶囊底框就会真溢出。

**修法**：`utils/layout.ts` 内置 **ASCII 0x20–0x7E 逐字符实测宽度表**（`ASCII_EM_TABLE`，95 项），标定口径：

- 字体：胶囊文本实际渲染的 **Segoe UI Bold**（`fontWeight="bold"` + `system-ui` 链在 Windows 的实际落点，与项目已有的 `capHeightRatio = 0.70` 同源基准）
- 方法：400px 逐字符 `advance ÷ 400`，再**向上取整到 0.05** ⇒ **对表内每个字符恒有「估算 ≥ 实测」**（结构性不欠估）
- 非 ASCII 统一 1.0em（汉字实测恰 1.000；希腊字母实测约 0.6，取 1.0 属有意的保守超估）

**校验结果**：表长 95 ✓、**欠估字符数 = 0** ✓、平均超估降至 **5.3%**；两句真实文案的超估由 +14.4% / +16.7% 降到 **+2.1% / +3.5%**。

### 4.3 两套 `estimateTextWidth` 命名分家

`src/utils/` 下原有两个同名 `estimateTextWidth`，模型不同（`layout.ts` 求胜、`labelOverlap.ts` 求稳），仅靠"barrel 不导出后者"避免冲突——这是**静默遮蔽**的定时炸弹。

判定：**不合并**（两者语义确有差异：胶囊底框要"贴紧"，标签避让要"宁可估宽"，合并会让避让变松而致标签重叠），改为**命名隔离**：

- `utils/layout.ts` → `estimateTextWidth`（胶囊底框，实测表）
- `utils/labelOverlap.ts` → **`estimateLabelTextWidth`**（标签包围盒，Unicode 区段 1.05 / 0.62 + 4px 余量），同步更新 2 处消费者（`ShiftPanoramaAxis.tsx`、`MarkovScene.tsx`）

这样即使将来有人把 `labelOverlap` 也加进 barrel，也不会互相遮蔽。

### 4.4 格式债按项目规范清理

`useCanvasSize.ts` 是 `src/utils/` 里唯一的"单引号 + 无分号"文件。经核查，**prettier 确为项目门禁**——`.husky/pre-commit` 执行 `npx lint-staged`，其配置对 `src/**/*.{ts,tsx,json,css,md}` 跑 `prettier --write`。即"被触及的文件本就该被格式化"。故本文件在被修改的同时按规范格式化（纯格式变更，无行为变化）。

### 4.5 量化影响（唯一的可见变化）
